# RK3588 上位机设计与对接方案

本文定义 RK3588 在整车里的职责、与 FPGA 的物理链路和报文用法、目标位置估计的要求、软件结构与联调步骤。
报文格式的唯一真值是 [icd.md](../2_interface/icd.md) 第 3 节与 `fw/nav/proto.c`；本文只规定怎么用、以及链路和扩展的计划。

## 0. 结论

**2026-10-27当前采用方案：** PNR61 / SYN49、SLF128、128KiB、原4500和双串口，实际BSRAM280/340且报告内部50/100MHz时序通过。板载CH以921600收发NV导航/地图，P11-40/A16以230400只发原126B控制V2；P11-39不启用，不补成外部速度入口。SFP Lane2独立千兆回显已通过，当前联合候选不含SFP。RK已部署Qwen3-1.7B、多模型视觉/语音、测量约束的任务层和地图上传/预览；小程序复用MediaMTX源走HLS。22:01公网只读为RK在线/real、导航和控制遥测offline，最近板上收尾为hold；真实地图接收和指令受理短测不等于落地导航通过。详见[总体设计](../system_architecture.md)、[PNR61签核](../4_design/g2_PNR61_signoff_20261027.md)、[落地建图指南](../3_guide/ground_debug_and_mapping_20261027.md)。

网页运行急停归零导航目标并保持平衡；IR5锁存、hold诊断与物理站稳另验。重连/复位不自动IDLE或续跑，重复STATUS不能刷新在线年龄。近期完整负载/USB重启后仍间歇残帧，具体根因未定；该缺口在RK接收/展示证据链，不据此推断片内控制失效。以下2026-10-21—24记录保留当时方案，涉及“当前只mock”“下一轮必须合SFP”的句子不再作为当前执行要求。

**2026-10-24 实测更新：** SFP1/P6/U11 的真实通道已更正为 Q0 Lane2，独立诊断镜像91FB与RK3588的eth2已建立1000Mb/s全双工链路；1/18/64/256/1472字节各20包，共100包原样回显通过，FPGA接收错误和回显丢弃均0。RK临时静态地址192.168.2.10/24，FPGA为192.168.2.100:9000；使用1000BASE-X/AN。此为独立短测，不代表NV应用或完整G2接受；原冻结Lane0候选不能作SFP1硬件验收。见[修正与交接](../4_design/sfp_mapping_correction_20261024.md)。

**2026-10-23历史顺序修订：** 当时要求打通SFP电口模块与RK通信，并计划合入共同工程；后续独立链路已测通，当前小场地PNR61选择双串口以收敛资源/时序。下面R0/R1/R2为选型背景，最新执行边界见本节10月27日说明和[总计划](../1_plan/system_integration_plan_20261021.md)。

**2026-10-21接口核对：** 控制仓库已经提供P11-39/40、230400 8N1的10字节直接速度命令和V2遥测；导航R0仍是921600调试桥/邮箱及NV任务报文，两者不同。以下职责是自主导航模式约定；直接速度调试模式可使用控制UART，但须显式退出导航控制并经过统一仲裁和失联保护。当前控制UART合法包后持续保持最后目标，尚无命令年龄看门狗。详见 [ICD第4.1节](../2_interface/icd.md) 和 [当前总计划](../1_plan/system_integration_plan_20261021.md)。

- **导航设计不依赖 RK3588**：目标架构在RK3588断开后由FPGA完成感知、定位、规划、避障、探索和底盘控制；当前导航与控制尚待统一顶层和整车验收（选题要求基础功能由 FPGA + 软核承担）。
  RK3588提供"任务和目标"：目标检测与跟踪、目标三维位置、多模型协同语义任务、网页展示与地图下发；当前并未部署图文联合VLM。
- **自主导航模式下RK3588不直接发连续速度**。它能发的只有 GOAL / WAYPOINTS / TARGET / MODE / SET_POSE / MAP_*；速度由 FPGA 规划并经 `safety_guard` 输出。
- 早期链路备选如下（当前执行顺序以上述2026-10-23修订为准）：
  1. **R0（现在就能用，FPGA 零改动）**：RK3588 的 USB 口接开发板的 USB 串口（CH9102），在 RK3588 上运行
     `python3 tools/nav_host.py --link uart:/dev/ttyACM0 …`（设备名以 `ls /dev/tty*` 为准，CH9102 也可能是 `ttyCH343USB0`）。
     这条路径 2026-10-01 已在板上用 PC 测通（[hardware_guide.md](../3_guide/hardware_guide.md) 6.1 节，本文第 3.2 节）。
  2. **R1（早期推荐，现为备选）**：RK3588 40 针排针的 3.3 V 串口接 P11 第 9 / 10 针，FPGA 增加一个硬件主机串口模块直通邮箱。
     改动小、几乎不占 BSRAM、不碰已验证的雷达网口。
  3. **R2（独立验证的SFP扩展）**：SFP1 + 高云1G Serial Ethernet IP，Lane2千兆回显已有实测；当前PNR61不采用。经交换机共用雷达RJ45仍是另一备选，不混同为当前双串口配置。

### 0.1 2026-10-23网口与应用准备情况

首次为源码核对；15:08—15:13已进一步只读登录RK与云服务器、读取在线API，并审阅Web设计会话。RK上的桥接、后端、感知、LLM/TTS确实运行，但导航与控制输入仍为mock，不能当作真FPGA链路验收。下面区分现有NV能力与完整Web需求，完整对接范围以0.2节为准。

| 部分 | 已有准备 | 尚缺的验收 |
|---|---|---|
| NV应用协议 | 导航C解析/处理、5Hz STATUS与MAP_ACK发送；PC/RK命令行及网页桥接服务 | 冻结双方版本，核对真实SFP收发与执行后的状态；模拟FPGA不能代替实际固件 |
| SFP硬件接口 | `integration/sfp/`独立MAC/PCS/SerDes、ARP/UDP回显、配置工具；独立PNR和专项仿真记录 | 实际电口模块的BASE-X/SGMII与协商方式、真实RK网卡/IP、物理收发与CDC核对；独立回显不解析NV |
| 联合工程 | 导航已有主机net_port和邮箱 | G2接入真实IP/CSR及125MHz收发域；完整资源/时序/CDC复验，旧331块不包含真实SFP |
| RK任务与视觉 | RK实机运行`yuntuo-fpga`分支2295129，桥接/后端/感知/LLM/TTS在线；Astra/YOLO状态及视频推流计数可读取 | FPGA收发仍连本机mock；相机外参配置不等于标定通过，真实测距/坐标/时间戳到FPGA尚未验收 |
| 停止与故障反馈 | 导航状态、独立控制UART遥测入口、内部命令监管原型 | 网口会话/命令确认、断链与恢复规则、实测停止反馈和物理停止包络，归N3联合验收 |

现有NV已实现的数据：RK下发GOAL/WAYPOINTS/MODE/SET_POSE、按视觉帧更新TARGET、需要有图定位时分块下发`.nvmp`；FPGA上发STATUS和MAP_ACK。这只是实现现状，**不是完整Web需求边界**。PATH虽有组包函数但当前应用没有发送，控制V2也没有合入SFP。网页地图可来自RK本地先验包或空白画布，不是已实现的FPGA实时地图上传。

此次明确发现的应用缺口：

- `STATUS.vx/wz`是导航指令。`QHXD_Web/yuntuo/bridge/tasks.py`的取消路径发出MODE idle后即提示“已停车”，找物完成分支用指令速度低于门限判断停稳；这些不能替代新鲜编码器/陀螺反馈。后续需区分“停止已请求”“指令已接受”“实际已停稳”。本次只记录，未修改另一个仓库的执行逻辑。
- NV v1无通用session/seq/命令ACK/有效期，地图ACK不承担运动确认。网页桥接的`found=0`保活用于建立回包地址，不提供FPGA失联制动；GOAL与自主任务是否在主机断线后继续、TRACK是否转探索，须按任务模式冻结并故障注入验证，不能笼统声称“掉网就停”。
- `nav_host.py listen`仅接收；对端地址未学习且未静态配置时，不能期望它自动收到首次STATUS。正式桥接已有无目标保活，应在握手验收中确认无运动副作用、单一指令来源和重连行为。
- 已读实现中TARGET的z/conf虽可解析，导航目标更新只使用平面x/y、延时、id与cls；置信度筛选在RK侧完成。GOAL末端yaw尚未启用，不能把可打包字段都当作已执行功能。

接续验收顺序：先确认独立SFP实物链路/ARP/UDP双向回显；同时准备真实SFP联合接入并通过资源/时序/CDC门槛；随后在执行器隔离条件下核对NV状态、地图及任务接收/取消；最后接入真实视觉坐标并与N3验证命令确认、断线/重连、实测停稳。实际运动另须满足当时供电/支撑确认和部署门槛。未定义完整协议前不把原始视频/点云塞入控制队列。

### 0.2 按实际Web需求补齐上下行合同（2026-10-23）

相机RGB-D、检测框/类别/置信度、带框H.264视频、语音/LLM及网页事件分别来自RK相机、感知、语音和后端服务，直接提供给Web/云端；它们不用绕经FPGA再返回RK。需要到达FPGA的是选中目标与任务结果。后续若提出FPGA原始点云等记录需求，再按真实用途、频率及存储接口评估，不把“目前没实现”当成永久排除条件。

**容量估算（建议配置，非实测速率）：** STATUS 44×5＝220B/s；完整V2 126×100＝12600B/s；以一条256个二维点、每点8B、约32B元数据计，路径2Hz约4160B/s；128×128单字节局部图2Hz为32768B/s；健康/应答暂留约640B/s。合计约50KB/s（约0.4Mbit/s应用数据）；若另上传一条同规模局部轨迹，再增约4KB/s。未含分片头、以太网/UDP开销、重传和先验地图下载突发。**此前只算STATUS/TARGET不足以代表整套Web需求**。这些数据量本身不大，但没有实链路吞吐/最坏时延结果，带宽余量也不等于FPGA资源与CPU余量。

资源与实现原则：命令/停止确认、健康和控制遥测优先，图块低优先且可降频/取消旧快照；不增第二套MAC/邮箱，不在FPGA复制一份16KiB栅格只为发送。现有A*可到256点而旧PATH一次≤32点，且路径内部为栅格坐标，需分片并明确地图/局部原点与比例，不能直接发送内部整数当世界毫米。快照一致性要靠版本校验与中止重取，不跨代拼图；若必须占用新缓存，计入完整联合资源。原物理331距336工作门槛只有5块，SFP及被恢复的发送逻辑、遥测接口净增均须真实综合/PNR，不能由50KB/s推导“资源影响很小”。

## 2. 现有报文怎么用（RK3588 侧规范）

报文为小端，公共头 `'N' 'V' 01 类型`；约定1024字节地图数据块对应1032字节NV报文，固件接收缓冲上限1100字节。FPGA 回复发往最近一次收到合法UDP报文的源地址（网口）或经串口回读。

| 报文 | 什么时候发 | 要点 |
|---|---|---|
| `MODE`（0x30） | 切换任务时 | 0 空闲、1 定点、2 跟踪、3 探索、4 急停（只是速度归零，不是安全急停）；重复发送无副作用 |
| `GOAL`（0x10） | 定点任务 | 无图：里程计系（上电或最近一次 SET_POSE 为原点）；有图：地图系；mm |
| `WAYPOINTS`（0x11） | 巡检路线 | ≤ 32 个点，`loop` = 1 循环 |
| `TARGET`（0x20） | 看见目标期间 **10–15 Hz** 持续发 | 见第 4 节；1.5 s 收不到新的就判丢失 |
| `SET_POSE`（0x12） | 有图模式开始时 | 地图系大致位姿，误差 0.5 m / 10° 以内；`flags` bit0 = 1 在先验图上对准 |
| `MAP_BEGIN / DATA / END / CLEAR` | 下发 `.nvmp` 先验地图 | 每块 ≤ 1024 字节，按 `MAP_ACK.next_offset` 续传 / 重发（`tools/nav_host.py upload_map` 已实现） |
| `STATUS`（0x80，FPGA → 主机，5 Hz） | — | 模式、状态、位姿、目标点、当前指令 vx / wz、标志、`t_us`、定位状态与质量；网页显示与任务状态机的输入 |
| `PATH`（0x81） | — | 格式已定义（`proto_build_path`），**固件目前没有发送**；网页要画路径时由导航组补上 |

RK3588 侧的报文编解码直接照 `tools/nav_host.py`（Python，可在 RK3588 上原样运行）或 `fw/nav/proto.c`（C）移植，不要另写一套字段定义。

## 3. 物理链路

### 3.1 方案对比

| 方案 | FPGA 改动 | RK3588 侧 | 带宽（有效） | BSRAM | 风险 | 用途 |
|---|---|---|---|---|---|---|
| R0 板载 USB 串口（调试桥 + 邮箱注入） | 无 | USB 线，`nav_host.py --link uart:` | 下发约 10–20 KB/s；回读每条 25–50 ms | 0 | 占用调试口：PC 不能同时用 `nav_uart.py`（可 SSH 到 RK3588 上执行） | **立刻开始联调** |
| R1 P11 第 9 / 10 针 3.3 V 串口（新增 `host_uart`） | 新 RTL 模块 + 约束 2 脚 | 40 针排针 UART，1.5–3 Mbps | 150–300 KB/s | 0–1 | 低：不碰雷达网口 | **比赛正式链路（推荐）** |
| R2a 交换机共用雷达 RJ45（百兆） | 雷达口协议栈增加主机 UDP 端口与邮箱分流 | 千兆网口 + 普通 UDP（`--link udp:192.168.0.100`） | 约 5 MB/s | 0–2 | 中：改动已验证的雷达链路；时序余量本来就小 | 想用以太网、或扫图时少插拔网线 |
| R2b SFP1 + 1G Serial Ethernet IP | 独立IP已生成，待接入`NAV_USE_SFP`（`nav_subsystem`已有主机口`h_*`） | 千兆网口 + 电口SFP模块 | 早期估计约50MB/s，未实测 | 完整联合净增未知 | 新增125MHz时钟域，需联合资源/CDC/时序与实物模块验证 | 当前正式主机链路方向，承载0.2节完整需求 |

带宽估算（仅两类应用报文）：TARGET 15 Hz × 24 B + STATUS 5 Hz × 44 B = 580 B/s，不含UDP/以太网开销、任务/地图/可选遥测；桥接代码当前TARGET默认上限12Hz。早期地图50–200KB是容量估算，实际以`.nvmp`文件为准。这类任务流量不是千兆带宽瓶颈，但MAC、跨域和缓存仍消耗FPGA资源；不能以流量小推断资源可以忽略。视频若另行决定传输，须单独估算吞吐/缓存；本次SFP接入已按用户要求推进，不再由视频需求决定是否启动。

### 3.2 R0：板载 USB 串口（现在可用）

- 接法：开发板 USB 串口口（CH9102，与 PC 调试用的是同一个口）→ RK3588 USB Host。921600 8N1。
- 原理：主机把报文逐字写进 `MBX.INJ_DATA`，写 `INJ_LEN` 后 `INJ_GO`，报文进入与网口相同的接收队列；FPGA 发出的报文留在发送缓冲，
  经 `MBX.TX_SEQ` / `MBX.TXB_ADDR` / `MBX.TXB_Q` 读回（[icd.md](../2_interface/icd.md) 第 3 节）。`nav_host.py` 的 `UartLink` 已实现。
- 代价：注入用流水写（`wr_burst`，不逐条等应答），一条 TARGET 约 1 ms；读回是逐字"写地址 + 读数据"，每次都有 USB 往返，
  一条 STATUS（44 字节、11 个字）约 25–50 ms。发送缓冲只保留最新一条报文，两次读之间 FPGA 连发多条时旧的会被覆盖
  （地图下发靠 `MAP_ACK.next_offset` 重新同步，不受影响）。所以 R0 适合 TARGET 10–15 Hz + 状态 5 Hz 的联调，不适合高频回传。
- 2026-10-01 已在板上用 PC 跑通这条路径（相当于 K0）：状态 5 Hz、目标点与模式生效、38964 字节地图包 1.7 s 下发"已加载"、
  探索模式下 10 Hz 的 TARGET 让 FPGA 切到跟踪，停发约 1.5 s 后判丢失并回到探索（接着雷达、有代价图时测的；没有代价图时规划步不运行，
  模式会停在跟踪）。RK3588 换成同一根 USB 线即可开始 K1。

### 3.3 R1：专用主机串口（计划，尚未实现）

该方案拟用P11-9/10，不是控制仓库已实现的P11-39/40速度串口；两者不能靠换两根线就互换。先用R0完成任务联调，G2资源过闸后再决定是否增加R1。

```text
RK3588 UART TX ──P11-9 (E16)───> host_uart: 字节流 → 帧同步 + CRC-16 校验 → 邮箱接收队列（与网口报文同一入口）
RK3588 UART RX <──P11-10 (D16)── host_uart: 邮箱发送缓冲 → 加帧头与 CRC → 串口发送
```

- 帧格式（建议，实现时写进 icd.md）：`0x7E` 定界 + 字节填充（HDLC / SLIP 风格）或 COBS；帧内容 = 原有 `'N''V'` 报文 + CRC-16-CCITT。
  报文本身完全不变，所以 RK3588 侧只换链路层，`nav_host.py` 增加 `--link serial:/dev/ttyS?` 即可。
- 波特率先用 **1.5 Mbps**：它是 Rockchip 板默认调试口的速率（串口时钟正好由 24 MHz 晶振分出），可靠；FPGA 侧 50 MHz / 1.5 MHz ≈ 33.3，误差约 1%。
  RK3588 的 UART 规格最高 4 Mbps，但 3 Mbps 以上没有官方稳定性数据，而且收发 FIFO 只有 64 字节（3 Mbps 时约 0.2 ms 就满），要开 DMA 或 RTS / CTS 流控，上板实测后再提速。
- 电平与引脚：常见 RK3588 板（Orange Pi 5 Plus、ROCK 5B）扩展口都是 **3.3 V**，可直接接 GW5AT 的 LVCMOS33，两板共地；Orange Pi 5（RK3588S）只有 26 针。
  扩展口上的 UART 默认多数是关的，要用板卡工具打开（Orange Pi：`orangepi-config`；Radxa：`rsetup` 打开 overlay，例如 ROCK 5B 的 UART7_M1 = `/dev/ttyS7`，
  40 针上同时有 CTS / RTS）。不要用 ROCK 5B 的 8 / 10 脚（默认调试控制台）。具体板卡以官方引脚表为准（资料来源：Radxa / Orange Pi 官方文档）。
- FPGA 侧：`host_uart` 接到 `host_mbx` 原来接主机网口负载的入口（`e_valid/e_data/e_last/e_err`），没有 SFP 时两者择一；
  发送侧复用 `net_port` 读邮箱发送缓冲的方式。预计 0–1 块 BSRAM（FIFO 用分布式 RAM）。
- 由导航组实现（RTL + testbench + 板级测试），RK3588 组实现 Linux 侧链路层。

### 3.4 R2 两种以太网方案的要点

- **R2a 交换机共用 RJ45**：雷达、FPGA、RK3588 接同一个傻瓜交换机，RK3588 设 `192.168.0.x`（不能用 100、101）。
  雷达只把 UDP 发给最近一次连它 TCP 的主机——导航运行时 **RK3588 绝不能连雷达的 TCP 7787**（包括厂家 SDK、上位机），
  否则雷达改发给 RK3588，FPGA 断流后 2 s 会重新抢回来，两边来回抢。扫图时反过来：先关 FPGA 的启动客户端（`NETL_CTRL` bit 6 写 0）。
- **R2b SFP**：RK3588 自身的千兆网口是 RGMII PHY，**不能插 SFP 模块**；做法是在 FPGA 板的 SFP1 笼里插一个电口 SFP 模块（1000BASE-T），
  用普通网线连到 RK3588 的 RJ45。电口模块的主机侧多数是带自协商的 SGMII，少数是 1000BASE-X，选型时确认，并在高云 IP 里选对应模式。
  板上 SFP1/P6/U11 经底板连接器实际走收发器第 2 通道（Q0 Lane2），参考时钟 MGT_CLK1（125 MHz）；此前第 0 通道记录错误，Lane0 实为 PCIe。实际适配入口为 `integration/sfp/sfp_host_mac.v`，见 [通道更正与实测](../4_design/sfp_mapping_correction_20261024.md)。旧 `Gowin_1GSERETH_Host` 名称属于早期占位，不能直接照搬实例端口。
  FPGA 地址 `NETH.IP` = 192.168.2.100，UDP 9000。

## 4. TARGET：目标位置怎么算、怎么发

FPGA 的处理（`fw/nav/target.c`）：收到报文的时刻减去 `latency_ms` 得到采图时刻，在位姿历史里插值出当时的机器人位姿，
把机身系目标点换算到里程计 / 地图系；之后机器人移动也不影响目标位置。探索（SEARCH）中收到 `found = 1` 自动切到跟踪（TRACK），
走到离目标 0.7 m 处停下并转向面对目标；1.5 s 没有新的 TARGET 判丢失，回到探索。只有探索模式会自动切换：空闲或定点时要跟踪，先发 `MODE 2`。
`found = 0` 的报文不会清掉目标，只是不刷新，丢失仍由 1.5 s 超时判断。

RK3588 必须保证：

| 项目 | 要求 |
|---|---|
| 坐标系 | **机身系**：原点 = 两轮轴线中点在地面的投影，X 前、Y 左、Z 上，单位 mm（与 [icd.md](../2_interface/icd.md) 第 1 节一致）。z 目前不参与规划，可填目标中心高度 |
| 相机外参 | 标定相机到机身系的旋转与平移（相机光学系 z 前 / x 右 / y 下 → 机身系 x = z_c、y = −x_c、z = −y_c，再加安装旋转与平移）；外参写进 RK3588 配置文件并留底 |
| 距离来源 | RGB-D 深度对齐到彩色图后，取检测框（或分割掩码）内深度的**稳健统计**（最近簇的中位数），不能取框内最小值；有效深度点太少时不发位置 |
| `latency_ms` | 从**图像曝光 / 采集时间戳**到报文发出的时间（用相机驱动给的时间戳，含推理耗时）。位姿历史 64 项（里程计 50–100 Hz 时覆盖 0.6–1.3 s），所以必须 **< 500 ms**，建议 < 200 ms |
| 发送频率 | 看见目标时 10–15 Hz；目标消失后发 `found = 0` 或停止发送（1.5 s 后 FPGA 判丢失） |
| `track_id` / `cls` / `conf` | 同一目标保持同一 id；`conf` 用千分比；FPGA 目前不按 cls / conf 过滤，过滤在 RK3588 做 |

验证：目标放在机器人前方 1 / 2 / 3 m、左右各 0.5 m，卷尺量真值，RK3588 输出与真值误差 < 5 cm（2 m 内）、< 10 cm（3 m）；
人举板子横向走动，`latency_ms` 估计偏小时 FPGA 换算出的目标位置会"拖尾"在运动方向后方，用这个现象检查延时。

## 5. 任务层：把语义任务翻译成报文

```text
用户指令（网页 / 语音） → VLM / 规则：要找什么、去哪里
      → 任务状态机（RK3588）
          巡检：当前RK桥接逐点GOAL（NV另有WAYPOINTS能力）
          找物：MODE search → YOLO 检测 + 属性确认（颜色 / 类别）→ TARGET 10–15 Hz → FPGA 自动跟踪
          定点：（有图）MAP_* + SET_POSE → 等 STATUS.loc_state = 2 → GOAL
      → 监视 STATUS：state（行进 / 到达 / 受阻 / 跟踪 / 探索 / 急停）、loc_state、flags
      → 结果上报网页
```

- 受阻（state = 3）持续时，任务层可以换目标点或回到探索，不要高频重复发同一个 GOAL。
- 有图模式里 loc_state 不是"正常 / 退化"时 FPGA 会原地保持，任务层只需等待并在网页上提示"定位中"。
- 任务层的一切决策都不能绕过 FPGA：不发速度、不直接操作底盘。

## 6. 网页（灵巡网页）与数据服务

| 网页内容 | 数据来源 | 现状 |
|---|---|---|
| 相机画面、检测框 | RK3588 相机 + YOLO（MediaMTX / WebRTC） | RK3588 侧 |
| 机器人位置、朝向、历史轨迹 | STATUS（5 Hz） | 协议已有；在线RK/Web当前仍mock，真SFP未验收 |
| 模式、状态、定位质量 | STATUS | 同上，不能以API在线判实车有效 |
| 规划路径 | PATH（0x81） | 格式已定义，固件未发送（导航组待办） |
| 局部代价图 | 待定义COSTMAP_TILE，原始128×128字节；明确代号/坐标/编码 | 已纳入正式需求；当前显示RK先验或空白画布，真图上行待实现 |
| 姿态、轮速、策略与故障、原始BMI/PID诊断 | 完整控制V2及其有效性 | RK已有解码，Web已有相关卡片；UART快照转SFP待实现，不能省成仅STATUS |

**安全提示**：FPGA 的主机报文接口（UDP 与串口）**没有任何鉴权**，谁能发包谁就能下目标点、切模式。
网页服务只开在比赛用的独立局域网 / 热点上，控制类接口（下任务、切模式）至少加口令，不要暴露到公网或校园网。

## 7. RK3588 软件结构建议

```text
rk3588/
  fpga_link/      报文编解码（照 tools/nav_host.py / fw/nav/proto.c）、链路层（R0 / R1 / R2）、心跳、日志
  perception/     相机驱动、YOLO26（RKNN）、跟踪、深度关联、目标三维位置（第 4 节）
  task/           任务状态机、VLM（RKLLM）、指令解析
  web_bridge/     网页数据接口（WebSocket / REST）、视频推流
  mapping/        录包、SLAM、调用 tools/map_tool.py、地图版本管理
  calib/          相机内外参标定与验证
  tests/          回放、假 FPGA（用 nav_host.py 报文构造）、延时测量
```

- 时间预算（目标）：采图 33 ms + 推理 30–60 ms + 深度与打包 < 10 ms ≈ 100 ms 级 `latency_ms`。
- 日志：每条收发报文记 RK3588 单调时钟，同时记下 STATUS 里的 FPGA `t_us`，联调时两边日志可以对齐。
- 当前TARGET丢失超时为1.5s，历史实现可转探索；正式失联/重连行为须按任务模式与N3冻结并验收，不把这一超时当命令租约，也不提前承诺所有任务可在RK断开后安全继续。

## 8. 扫图中的角色

RK3588（aarch64，Ubuntu 20.04 以上，厂家 SDK 支持）可以承担录包、离线 SLAM、`tools/map_tool.py build` 和下发，详见 [mapping_plan.md](../1_plan/mapping_plan.md)。
两条纪律：扫图时由录包的机器连雷达 TCP，先关 FPGA 的雷达启动客户端；导航时任何上位机都不能连雷达 TCP（第 3.4 节）。

已决定（写回记录）：

- **目标测距仍用 RGB-D，不把雷达深度流转发给 RK3588**（2026-10-17，导航组与视觉组确认）。评估过的替代方案与放弃原因留档：
  原始深度帧 160 × 60 × 2 B × 10–15 fps ≈ 2–3 Mbit/s，R1 串口带不动，只能走雷达组播直收（零 FPGA 开发，但雷达组播支持待实物验证）

  室内 0.3–5 m。以后若要做网页点云显示，可单独评估雷达组播直收，不影响本决定。
